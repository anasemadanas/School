# Conceptual Model

The conceptual model describes the business: which things the school keeps track of, and how they relate. It has no attributes and no data types.

| Diagram | Content |
|---|---|
| [diagrams/conceptual/master_conceptual.puml](../diagrams/conceptual/master_conceptual.puml) | All 15 schemas. Every entity is grouped by module, with the cross-module relationships. The 5 reserved schemas appear as empty dashed packages. |
| [diagrams/conceptual/modules/*.puml](../diagrams/conceptual/modules) | One diagram per module (finance is split into *setup* and *billing*). Every entity and every relationship has its cardinality and a verb phrase. |

## How the three levels stay consistent

The conceptual, logical and physical diagrams are all generated by `tools/generate_diagrams.py` from one model, which it parses from the T-SQL scripts. As a result:

- The **entities are the same** at every level. A conceptual entity name is the business singular of the table, for example *Person* for `people.Persons`.
- The **relationships are the same** at every level. Each conceptual relationship is one foreign key, labelled with a verb at the conceptual level, with the key name at the logical level, and with the constraint at the physical level.
- The **cardinality** of every relationship comes from foreign-key nullability and uniqueness, so it can't differ between levels.

Only the *detail* changes from level to level: names only → attributes with generic domains → SQL Server columns, types, constraints and indexes.

## Business concepts by module

| Module | Main concepts | Key relationships (conceptual reading) |
|---|---|---|
| **organization** | School, Branch, Building, Room, Room Type, Department, Country, Document Number Series | A school *operates* branches. A branch *contains* buildings, which *contain* rooms. |
| **iam** (the "identity" module) | User Account, Role, Permission, Role Permission, User Role | A person *signs in with* at most one user account. An account *is granted* roles, optionally limited to one branch. |
| **people** | Person, Student, Guardian, Employee, Teacher, Student Guardian, Person Contact, Person Address, Person Identity Document | A person *may be* a student, a guardian and/or an employee (overlapping roles). An employee *may be* a teacher. A student *is cared for by* guardians (many-to-many). |
| **academic** | Academic Year, Term, Holiday, Grade Level, Program, Subject, Curriculum Subject, Section, Teaching Assignment | A school *runs* academic years. A year *is divided into* terms and *opens* sections. A teacher *teaches* a curriculum subject to a section. |
| **enrollment** | Application, Application Status History, Enrollment, Section Assignment, Enrollment Subject | A person *applies through* applications. A student *is enrolled through* one enrollment per academic year. An enrollment *is placed* into sections over time. |
| **timetable** | Bell Schedule, Period, Timetable, Timetable Entry | A section *is scheduled by* versioned timetables, which *consist of* entries (day × period → teaching assignment and room). |
| **attendance** | Attendance Session, Attendance Record, Attendance Status | A section *takes roll-call* in sessions. A session *records* one mark per enrolled student. |
| **assessment** | Grading Scale, Grading Scale Band, Assessment Type, Assessment Weight, Assessment, Assessment Result, Report Card, Report Card Line | A teaching assignment *is evaluated by* assessments. An enrollment *earns* results and *receives* versioned report cards. |
| **finance** | Currency, Fee Type, Fee Structure, Fee Structure Item, Fee Installment, Discount Type, Student Discount, Sponsor, Payer, Student Payer, Invoice, Invoice Line, Credit Note, Payment Method, Payment, Payment Allocation | A fee structure *prices* a year, branch, grade and program. A payer (a guardian **or** a sponsor) *is responsible for* enrollments, *is billed* invoices and *pays*. Payments *settle* invoices through allocations. |
| **audit** | Audit Event, Security Event, plus temporal history | Every business procedure writes an audit event. SQL Server keeps every version of the system-versioned entities. |
| hr, transport, library, inventory, communication | None: empty schemas reserved for future expansion | No entities. Possible extensions are described in [FUTURE_EXPANSION.md](FUTURE_EXPANSION.md). |

## Core business process (end to end)

```
Admission (Application) ──accepted──▶ Enrollment per Academic Year ──▶ Section Assignment
      │                                        │                              │
      │                                        ▼                              ▼
      │                               Fee Structure ─▶ Invoice ◀── Payer ─▶ Payment (allocated)
      ▼                                                                       
 Person (+ Student role)          Timetable ─▶ Attendance (daily) ─▶ Assessments ─▶ Report Cards
                                              every step ──▶ Audit trail
```

## Concepts that are deliberately *not* entities

- **No "Student Limit" or "School Capacity" entity.** Capacity is an optional attribute of Section and Room only.
- **Role** (Student, Guardian, Employee) is not a stored type code. A person's role is the existence of a subtype record, which allows overlapping roles. See [CATEGORICAL_MODEL.md](CATEGORICAL_MODEL.md).
- **Invoice status, enrollment status and similar values** are states of an entity, not subtypes of it.
